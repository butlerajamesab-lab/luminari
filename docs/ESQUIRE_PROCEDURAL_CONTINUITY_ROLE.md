# Esquire Procedural Continuity Role

Date: 2026-05-13
Repository scope: active Lighthouse/Luminari V1 repo
Esquire repository: `https://github.com/butlerajamesab-lab/esquire`
Esquire Supabase project ref: `eombkfyeymqqjanlunal`

## Scope

This document records Esquire's platform role from the perspective of Lighthouse recovery. Esquire is the pro se litigant and procedural-continuity substrate. Lighthouse may route users toward Esquire and consume Esquire-facing composition states, but Lighthouse does not own Esquire's case model, offline storage, crisis-mode behavior, RLS policies, or full-view composer.

Esquire should not be built or described as a generic AI legal assistant. Its core role is to maintain procedural reality for a human being over time.

---

## Core Definition

Esquire is the survivability layer between a human being and hostile or opaque procedural systems.

It operationalizes the rest of the Luminari stack for one person:

```txt
Atlas context + Lighthouse signals + Rosetta law constants + Prism reasoning -> Esquire procedural continuity
```

Esquire's mature goal is not merely document generation, chat, or intake automation. Its mature goal is stateful procedural navigation under institutional asymmetry.

---

## Three Esquire States

| State | Meaning |
| --- | --- |
| Current Esquire | backend contract, case-view layer, composition surface for Rosetta/Prism/Lighthouse, pro se intake direction, procedural orchestration shell |
| Hidden Esquire | person-to-procedure path: intake, rights translation, contradiction detection, evidence organization, escalation routing, survivable action sequence |
| Future Esquire | adaptive procedural co-navigation that remembers state, tracks timelines, detects traps, maps obligations, preserves provenance, and escalates intelligently |

---

## Correct Stack Position

Esquire sits downstream from law, reasoning, and systemic context. That position is intentional.

A pro se user should not have to understand:

- ontology layers
- provenance schemas
- extraction pipelines
- signal normalization
- legal decomposition tables
- bridge mechanics

Esquire absorbs that complexity and emits:

- clarity
- sequence
- obligations
- risks
- missing evidence
- deadlines
- next actions
- court-ready or agency-ready outputs

---

## Core Object: Procedural State

Esquire's core object is not a chat, document, or generic case. Its core object is procedural state.

Examples:

- waiting for response deadline
- evidence gap exists
- appeal window closing
- contradiction unresolved
- agency failed statutory obligation
- missing mandatory filing
- retaliation risk elevated
- notice period running
- filing sequence incomplete
- safety/courtroom preparation required

The platform value is procedural continuity under pressure.

---

## What Esquire Should Own

Esquire should own:

- user-owned pro se case view
- full-view composer
- procedural state model
- offline-first capture and sync behavior
- crisis-aware UI state
- local evidence organization
- recording/consent safety checks where applicable
- user-facing action sequence
- court or agency bundle composition
- alternative interpretations / causal firewall presentation
- narrative bias warnings and platform self-limitation surfaces
- final human-readable procedural continuity layer

---

## What Esquire Should Not Own

Esquire should not own:

- Atlas ingestion or reference authority
- Lighthouse signal detection or governance gate
- Prism validation/escalation truth authority
- Rosetta law-to-constants schema
- public stream ingestion
- systemic pattern production
- final legal authority or legal-advice claims

---

## Essential Engines

### Canonical Intake Ontology

Esquire needs canonical intake schemas, event types, harms, procedural states, evidence types, jurisdiction mappings, and route classifications. Without this, routing, recommendations, escalation logic, and UI behavior will drift.

### Temporal Engine

Esquire needs time-awareness beyond timestamps:

- statutory deadlines
- response windows
- appeal windows
- escalation triggers
- tolling events
- procedural pauses
- notice periods
- retaliation windows
- filing sequence constraints

### Contradiction Engine

Esquire should surface contradictions between stated policy, required procedure, actual institutional conduct, and user evidence. Prism may validate reasoning and contradictions, but Esquire must translate contradiction state into survivable next steps.

### Procedural Continuity Engine

This is Esquire's most important capability. It exists because people lose cases through fragmentation, exhaustion, missed deadlines, cognitive overload, contradictory instructions, disappearing paperwork, and institutional asymmetry.

## Human-State Design Rules

Esquire is protective by design.

It should prefer:

- calm sequencing over dense analysis
- continuity over novelty
- explicit unavailable states over false confidence
- local/offline capture over network dependency
- source-linked statements over ungrounded conclusions
- narrow next actions over broad legal speculation
- crisis-safe capture over forced review

In crisis mode, the interface should narrow to preservation and safety: record, tag, save, exit if needed. Analysis and review can wait.

---

## Integration Rules

Allowed inbound inputs:

- Atlas jurisdiction/resource context through verified contracts
- Lighthouse governed signal context and civic pattern context
- Rosetta validated law-to-constants outputs
- Prism validated findings, contradictions, reasoning summaries, and escalation readiness

Allowed outbound outputs:

- user-owned procedural state
- full-view case composition
- source-linked evidence bundles
- generated filing/checklist state
- user-facing next-action sequence
- bounded status signals back to Lighthouse/Prism when explicitly permitted

Forbidden behavior:

- presenting generated analysis as legal advice
- suppressing uncertainty or unavailable states
- replacing Rosetta validation with ad hoc law interpretation
- replacing Prism verification with UI confidence
- requiring continuous connectivity for core capture
- forcing a crisis-mode user into analytical review

---

## Lighthouse Consumption Rule

Lighthouse should treat Esquire as the downstream procedural-action substrate. Lighthouse can route users to Esquire and display Esquire status summaries, but Lighthouse should not absorb Esquire's full case model or crisis/offline behavior into Lighthouse schema during recovery.

Correct boundary:

```txt
Lighthouse contextualizes harm and patterns.
Esquire maintains procedural reality for the person over time.
```

---

## Maturity Interpretation

Esquire's architectural potential is extremely high because it is not trying to automate lawyers. It is trying to reduce procedural asymmetry, cognitive overload, institutional opacity, and continuity collapse.

The danger is becoming a generic AI legal assistant, document chatbot, or intake automation tool. Esquire's unique property is stateful procedural navigation under institutional asymmetry.
